# Security

All code in this platform is public on GitHub. This document assumes that as a given, not
a risk — nothing here relies on the source being secret.

## Secrets

**AWS Secrets Manager is the sole authoritative store for application secrets.** Nothing
below is ever committed:

- Shopify Admin API tokens / webhook signing secrets
- Database credentials
- SMS provider API keys
- Any future third-party API credential (QuickBooks, Stripe, ad platforms, etc.)

Database credentials are generated by Terraform (`rds-postgres` module, in
`hegarty/terraform`) and written directly to a Secrets Manager secret — they never appear
in a `.tfvars` file, Terraform state is the only place the value transits, and state itself
is never committed (see that repo's `.gitignore`). Shopify tokens and the SMS provider key
are empty Secrets Manager "shells" provisioned by Terraform and populated out-of-band, by
hand, after `apply` — see `eks-prod`'s `workloads/commerce-intel/secrets/` units.

Every `shop_*` service reads its secrets from Secrets Manager at startup via its EKS Pod
Identity role (see below) — never from an environment variable holding the raw value,
never logged.

## Pod-to-AWS identity: EKS Pod Identity, not IRSA

Each service (`shop_ingestor`, `shop_analytics`, `shop_notifier`) has its own narrowly
scoped IAM role, associated to its Kubernetes ServiceAccount via **EKS Pod Identity**
(`aws_eks_pod_identity_association`) — not the older IAM-Roles-for-Service-Accounts (IRSA)
pattern. Pod Identity doesn't require a per-cluster OIDC provider and is the currently
recommended approach for new EKS workloads. Each role's policy is scoped to exactly what
that service needs:

- `shop_ingestor`: `s3:PutObject` on the raw archive bucket, `secretsmanager:GetSecretValue`
  on the Shopify token and DB credential secrets.
- `shop_analytics`: `secretsmanager:GetSecretValue` on the DB credential secret,
  `s3:GetObject`/`ListBucket` on the raw archive (reprocessing only).
- `shop_notifier`: `secretsmanager:GetSecretValue` on the SMS provider secret only.

No service has `s3:*`, no service has a wildcard IAM policy, no service is
`AdministratorAccess`. See `hegarty/terraform`'s `eks/pod_identity` module and
`eks-prod`'s `workloads/commerce-intel/pod_identity/*` units for the exact policy JSON.

## Network: Cilium

Cilium is the primary CNI on `eks-prod`, used intentionally (NetworkPolicy, Gateway API,
Hubble), not merely as the installed networking plugin:

```
shop_ingestor    -> Redpanda
normalizer       -> Redpanda, PostgreSQL   (same binary as shop_ingestor)
shop_analytics   -> PostgreSQL, Redpanda
shop_notifier    -> Redpanda, approved external notification APIs only
```

Default-deny is the goal for the `commerce-intel` namespace; every other east/west path is
explicitly denied. Exact `CiliumNetworkPolicy` manifests live in `eks-prod/manifests/` —
see that repo once the policies are written (tracked, not yet implemented as of this
writing).

## Webhook authenticity

Every inbound Shopify webhook is verified via HMAC-SHA256 against the webhook signing
secret before any processing — this happens in `shop_ingestor` before the payload touches
the event bus. Requests that fail verification are rejected with `401` and never published,
logged, or archived (a forged payload doesn't belong in the raw archive either).

## Logging and PII

Raw Shopify webhook payloads may contain customer PII (name, address, email). Structured
logging (`shop_platform/logging`) never logs a raw payload body. HTTP headers are always
routed through `logging.RedactHeader` before logging, which redacts `Authorization`,
`X-Shopify-Hmac-Sha256`, `X-Shopify-Access-Token`, `Cookie`/`Set-Cookie`, and `X-Api-Key`
regardless of log level.

## Encryption

- **At rest**: RDS (`storage_encrypted = true`), S3 (SSE-S3/AES256), Secrets Manager
  (encrypted by default), EBS volumes (encrypted, set at the node/PV level).
- **In transit**: RDS connections require `sslmode=require` (see
  `shop_platform/db.Connect`); the OTel Collector and Redpanda are in-cluster-only,
  reached over the cluster network rather than a public endpoint.
- **Keys**: AWS-managed keys (`aws/s3`, `aws/rds`, `aws/secretsmanager`), not customer-
  managed keys (CMKs) — a documented MVP cost tradeoff (each CMK is a fixed monthly cost).
  Revisit if a specific compliance requirement demands customer-controlled key rotation.

## CI-level controls

Every `shop_*` repository runs, on every PR: TruffleHog (secret scanning, fails the build
on any verified or unverified finding), `go vet`, `go test -race`, `golangci-lint`
(including `gosec`), `govulncheck`, GitHub native secret scanning + push protection, and
CodeQL. Branch protection requires all of these to pass, requires GitHub-verified signed
commits, and blocks force-push/deletion on `main` — enforced and continuously verified by
[`github_policy-as-code`](https://github.com/hegarty/github_policy-as-code), not by hand.
